# Community Hub data model proposal

**Status:** Conceptual only; no models or migrations have been created. Requires owner approval and a selected, tested migration/recovery strategy before implementation.

## Existing identity and membership (reuse)

- `User.id` is the account identity and foreign-key target; reuse it for every Hub-owned record.
- `User.status`, `User.is_admin`, `MembershipDetails.date_of_birth`, `MembershipDetails.membership_type`, `MembershipTerm` and existing consent/preferences are current sources. They are not yet a sufficient centralized policy API. Confirm payment and expiry semantics before treating status as authorization.
- Do not copy legal name/email/DOB/guardian data into profile or directory records.

| `MemberProfile`                                | One-to-one `user_id`; selected `display_name`, biography, general community, standardized interests, participation goals, optional moderated photo reference, moderation state, timestamps.                                                         | One profile per existing account. Never stores or exposes verified/legal identity. Youth profiles excluded from adult discovery.                                |
| `ProfilePrivacy` or profile visibility columns | Directory opt-in (default false) and independent visibility for community/interests/goals/biography/photo.                                                                                                                                          | Server-side query and serialization enforcement. Avoid a default-visible migration.                                                                             |
| `ProfileHighlight`                             | `user_id`, source verified activity/volunteer record, member-selected visibility, moderation/status and timestamps.                                                                                                                                 | Only own verified records may be selected. Must not surface sensitive/private activity. The source record shape requires owner decision.                        |
| `Activity`                                     | Creator/primary organizer, title/description, category, start/end and timezone, location granularity, capacity, accessibility, equipment, requirements, safety info, registration mode, official/member classification, state, version, timestamps. | Draft → review → approved/published → changed/cancelled/unpublished transitions. Public detail excludes roster and unnecessary precise location.                |
| `ActivityReview` / `ActivityVersion`           | Activity/version, reviewer, decision, request-changes/reason and timestamp; preserve significant versions.                                                                                                                                          | Admin-only review; audit transitions; approved changes may require renewed review.                                                                              |
| `ActivityOrganizer`                            | Activity, user, role/status, inviter and approval metadata.                                                                                                                                                                                         | Primary organizer invites co-organizers; admin must approve; access scoped to assigned activity.                                                                |
| `ActivityRegistration`                         | Activity/user, state, created/updated, approval and cancellation details.                                                                                                                                                                           | Unique `(activity_id, user_id)`; current active-member check at registration and before event; only minimum roster fields visible.                              |
| `WaitlistOffer`                                | Registration/activity, FIFO position or sequence, state, expiry, idempotency key and timestamps.                                                                                                                                                    | Transactional capacity and promotion; never exceed capacity; provisional 24-hour offer needs approval.                                                          |
| `AttendanceRecord` / `VolunteerHours`          | Activity/user, attendance, submitted hours, verifier, correction history/reason and timestamps.                                                                                                                                                     | Organizer-scoped submission; admin verification; preserve correction history.                                                                                   |
| `Connection`                                   | Canonical pair of adult user IDs, status (requested/accepted/declined/disconnected/blocked), requester and timestamps.                                                                                                                              | Unique unordered pair; active-adult checks; block prevents further contact/request; anti-spam limits. | `Conversation` / `Message`                     | Conversation between two eligible accepted connections; text-only body, sender, timestamp, moderation/report references as appropriate.                                                                                                             | No attachments/read receipts/presence. | `HubAuditEvent`                                | Actor, action, entity type/id, timestamp and non-sensitive before/after metadata.                                                                                                                                                                   | Append-only by application convention; never record passwords, tokens or message bodies. Limit sensitive personal data.                                         |

## Indexing and integrity guidance

- Add foreign keys and indexes for ownership, activity state/start time, registrations by activity/state, waitlist order/expiry, directory filters only after query patterns are tested, unread-message lookup and moderation queue state.
- Enforce profile one-to-one, registration uniqueness, valid connection pair ordering/uniqueness, valid state transitions and nonnegative capacity/hours with database constraints where practical.
- Capacity reservation and waitlist promotion require a transaction and a database-appropriate lock/atomic update. Concurrency behavior must be tested on PostgreSQL, not inferred from SQLite-only tests.
- Use UTC timestamps for instants and store an IANA timezone for activity display/scheduling.
- Store photos outside the relational database through an approved managed storage provider; do not store arbitrary paths or trust client-supplied MIME types. Upload support is deferred until provider, moderation, limits and deletion policy are approved.
- Keep audit events separate from ordinary logs; redact sensitive details.

## Migration strategy questions

The app currently uses `create_all`, with no checked-in migration history. Select an existing-convention-compatible migration framework and establish tested backup/restore plus rollback/safe-recovery procedures before schema changes. Production migration execution and deployment require explicit approval. Initial schema proposal must be reviewed against the actual PostgreSQL version and concurrency behavior.
